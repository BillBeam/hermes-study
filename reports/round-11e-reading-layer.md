# R11E:阅读层 —— 三份派生件,一道防手抄的关卡

**一句话结论**:派生件只能生成,不能手抄。

本轮不吃新内容、不改动 `chapters/` 正文,只为「单一读者按能力域学透、并在工作中随时检索」
新增一层阅读入口。三份派生产物 + 一道**落地即阻断**的防漂移关卡。
派工三片(A / B 问题索引各半,C 移交归属),主线做防漂移机制、原则层、合并、
全部制度裁定与复核。

**分片顺序是强制的**:关卡与制度必须在派发子代理**之前**落地(边界明令),
而原则层的冲突裁定是本轮唯一必须由主线亲做的编辑判断——它是要写进《设计蓝图》
读者手里的裁决,不能转包。

## 2. ★ 防漂移:两道锁,分工不同

验收把这一项列为第一位。机制是**声明式**的,与本项目其他关卡同源。

**锁一(产物钉)**:三份产物由 `scripts/build_reading_layer.py` **全生成**——凡引自成品章的
文字一律**运行时逐字抽取**,不经人手。关卡重建后与库内文件**逐字**比对,不一致记
`PRODUCT-STALE`。

**锁二(源节钉)**:每个被派生件引用到的成品章小节,按「H2 标题 + 节正文」算一个 sha256
钉在 `data/r11e/section-digests.tsv`(收工 **134 个**)。对不上记 `SECTION-DRIFT`,
**生产者自己也拒绝构建**。

**为什么必须是两道。** 只有锁一时,作者可以一句 `--write` 把源章的新内容刷进产物,
**而没有任何人重新读过那一段**——源章改了、产物跟着改了,却没人判断过「这条原则是否还成立、
这个问题索引是否还指对地方」。锁二让「我重读过了」成为一次**显式的、会进 diff 的**动作
(`--restamp`)。**锁一防的是忘了同步,锁二防的是不假思索地同步。**

另有 `ANCHOR-UNRESOLVED`(章内锚点解析不到真实标题)、`UNSTAMPED` / `STALE-STAMP`,
以及 `EMPTY-GATE`(三类比对数任一为 0 即失败)。

### 2.1 负控:19 条断言,证明它拦得住、且不是空绿

`data/r11e/probes/reading_layer_negative_control.sh` 全程在 `mktemp -d` 的**临时副本**里做
——本轮边界写死 `chapters/` 零改动,而一个「临时改一下再改回来」的负控,
会在它运行的那几秒里让并发的 git 操作看见一棵被改过的树。

**「不是空绿」这一项是怎么证的**(验收明确要求):`NC1b` 断言关卡判绿时
`sections/products/links` 三个读数**同时 >0**;`NC6` 反过来证明这三个数为 0 时关卡**开火**。
两条合起来,「绿」这个信号必然伴随一个可当场核的 N —— 这正是 R8C 记下的那个形状
(锚点全写在块后的文件,关卡输出 `OK` + 退出码 0,一条都没校验)。

**落地即阻断,不走分期**:守的三份产物是本轮新增的,积压恒为 0,不存在「关卡对着自己
没造成的积压狂叫」。与 R9B 表格锚点、R11C 可跑性检查同例。

**覆盖面如实说**:关卡守的是三份产物、以及它们**引用到的**那 134 个小节。`chapters/` 里
**没被任何派生件引用**的小节改了,本关卡沉默。它把下限从「派生件没人管」抬到
「**派生件引用到的源节一改必被拦**」,不是「`chapters/` 全被守住了」。

——列表项 / `**①…**` 段 / `**(1)…**` 段。

| | 数 |
|---|---:|
| 合并前源条目 | **169** |
| 合并后原则 | **59** |
| 跨章冲突裁定 | **5** |
| 本合集引用到的源条目 | **169(100.0%)** |
| 压缩比 | 169 ÷ 59 ≈ **2.9 : 1** |

**这个 100% 是改出来的,不是一次写对的。** 第一版只引用 115 条(68.0%)。
合并账是**脚本算的**、印在产物末尾,于是它当场把漏掉的报了出来:
漏的里面有**整整一族**(凭据与外发,4 条原则),还有**四条我在编辑正文里引用了、
却没有声明来源**的条目——正是本层要防的手抄形态,只不过出在编辑侧而不是产物侧。

### 3.2 合并了哪些组、依据是什么

**合并依据分三类**,每条在产物里都写了 `merge-why`:

1. **同题异述**(最多):多章各自撞见同一条,措辞不同、形状相同。P04 五处的措辞是
   缝 / 调用点 / 工具名 / 注册表,合并后能看出这是**被独立印证次数最多的一族**之一,
   而这个事实本身就是这条原则强度的证据——**按章排列时它看不见**。
2. **上下位**:一条给一般形式、另一条给限定条件。P08 合并后把各章补的限定条件接了起来
   (多份实现可以有,但每多一份必须**同时**交付可执行断言;而断言本身还有作用域问题)。
3. **同章聚合**:P40 五条全出自第 8 章,不是重复而是**同一个动作上五个各自独立的坑**。
   放在一起才构成可照做的检查表——这正是「以原则为条目」相对「以章为条目」的收益:
   同章五条被聚成一条清单,而不是散在一个 24 条的长列表里。

**「印证 N 章」这个数自己出过错**:目录里第一版数的是 `src` 声明条数而不是**不同的章**,
P01 / P04 因此各虚高一章。改为数不同的章,并在两数不等时**两个都打出来**
(`印证于 4 章 / 5 处`)。这是本轮生成器自己造的手抄式错数,记在此处。

### 4.2 合并:词表能统一,措辞不会

两片用**同一份固定十格词表**,`NEW:` 提议 0 个,合并时零词表冲突。但——

**A 118 问题 / B 115 问题,逐字相同的 0 个。** 产品按 `group` + `problem` **逐字**合并,
于是**措辞就是主键**,而两片独立写出的同一个问题必然写法不同。

合并用**声明式**归一化表(`data/r11e/probes/merge_problem_index.py`):**7 条**改写,
全部命中(表里有一条没匹配上就 FAIL,防止原文被改后归一化悄悄失效);
另有 **4 组**近义对**有意不合并**并逐条写明理由——一个只记录「合并了什么」的表,
读者无法判断没合并的是漏了还是有意的。**不做模糊匹配、不算相似度**:
一个靠相似度合并的索引会把两个不同的问题并成一个,而读者无从发现。

7 条归一化里最值得记的一条:「升级到一半崩了」两片连**域**都判得不同
(A 判部署、B 判可靠性)。裁定归**部署、运维与升级**——升级是交付链上的动作,
放进「可靠性」会让读者在故障域里找部署问题。

## 5. 本轮不产出成品章,依据

1. **没有新机制可讲**。成品章的定义是「求读的机制讲解,构成 R12《设计蓝图》正文」,
   其内容来源是底稿的机制证据;本轮不吃新内容,**零新增机制证据**。
2. **边界不允许**。边界明令不重排章序、不合并章节;新增一章会把章序落点表从 21 改到 22,
   与「装订轮需要一个未被动过的起点」直接冲突。
3. **派生层不该装订进正文**。三份产物是「求读」的,但它们是**派生层**:装订进正文
   会让正文与派生层互为副本——正是本轮原则层 **P08** 要防的形态。派生层的正确位置
   是正文**之外**的入口。
4. **有先例**:`data/round-registry.tsv` 里 R8-fix(评审处置轮)、R11C / R11D(元工作轮)
   的 `chapter` 列均为 `-`。R11E 记为**阅读层轮**。
