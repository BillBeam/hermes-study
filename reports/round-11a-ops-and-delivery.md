# R11A · 运维基建 L2 + skills L3 校准片

**一句话结论**:9 倍文件只贵 1.26 倍,L3 按行走。

本轮两件主体事:吃下台账 `round=R11` 名下的**运维基建 L2**(141 文件 / 43,365 行),
以及从 `round=R6` 的 L3 桶里取一片 **skills 校准片**(118 文件 / 17,619 行),
量出「同构短文档」这一形态的 L3 真实单位成本。合计 **259 文件 / 60,984 行**。

**为什么合并成一轮。** R10B 的建议是"R11A 明显偏小(本轮的 20%),与清账部分合并,
不单开一轮"。本轮采纳,依据是实测的容量带而不是感觉:R10 与 R10B 合计 21 片,
每片 17,544–22,551 行。43,365 行按这个带切正好 **2 片**,再加 1 片校准片 = 3 片,
仍在单轮可承载范围内。**单独开一轮 2 片的轮次,收官成本(报告、成品章、台账、
全量关卡)与 11 片的轮次几乎一样**,而这些固定成本才是小轮次真正的浪费。

### 1.1 H-R10B-a 结清:无扩展名文件的锚点

`.gitignore:3`、`Dockerfile:12`、`docker/s6-rc.d/main-hermes/run:23-26` 这类锚点

移交项明写"修法与 H-R10-a 不同:需显式文件名单,不能放宽正则"。这是一条设计断言,
所以本轮先给它一个数:`data/r11a/probes/extless_name_census.py` 把**嗅探式**的替代方案
(接受基线里任意无扩展名基名 + `:数字`)拿全语料跑一遍,结果是
**26 处真锚点 + 1 处非锚点**。一比二十六不算灾难,但它是**错的那一个**:
`reports/round-5` 里的 `base:645` 是 `base.py` 的简写,哪儿都解析不到;
而 `base`/`run`/`type`/`finish`/`dashboard` 既是 `docker/s6-rc.d/` 下的真文件、
又是普通英文词——嗅探式方案的错误率是**这个语料的词汇的函数**,不是一个上界。

所以按移交项的要求做:**声明一份名单**(`EXTLESS_NAMES`,26 个,取自基线实际存在的
无扩展名文件),**并给歧义词加上与 ccTLD 守卫同一句话的条件**——要多一点
"它是个路径"的证据:有目录部分,或者能解析。

**读数(三个,分别标注,不合并)**:

| 口径 | 数 |
|---|---|

| 关卡新计入的 **table_anchors** | **+1** |

26 与 20 的差额**逐项对上了**,不是"大概吧":4 处在围栏块内(关卡按设计不扫块内),

`data/r11a/probes/extless_delta_reconcile.py`:

**负控(验收项 ①)**:`data/r11a/probes/extless_negative_control.py` 造一份夹具,

- **正控**:一条**正确**的锚点必须记 OK。否则一份纯粹畸形的夹具也会"全红",看起来像关卡在工作。
- **总数断言**:断言 `citations=` **恰好等于**植入的锚点数。被吞的串通常安静地记成

- **漂移落点非空行**:夹具改过一版。初版有一个漂移锚点正好落在**空行**上,
  那是一种看起来在证明、实际上什么都没证明的形态(CLAUDE.md 讲 BLOCK-DRIFT 时点名过)。
  现在每个漂移目标都强制落在**有内容的行**上。

## 3. L3 校准:第二个数据点,以及它决定了什么(验收项 ③)

### 3.1 片怎么取的

`round=R6` 那个桶不是**一个**总体。形态普查(`data/r11a/probes/skills_bucket_profile.py`)
给出的分布:中位文件 156 行,最大 16,799 行;42 个类目的"行/文件"跨度 **1,195 倍**;
**316 个技能目录里 22 个就占了全桶 52.6% 的行数**。

而那 22 个根本不是"同构短文档":最大的是
`optional-skills/mlops/training/unsloth`(29,016 行 / 5 文件 = 5,803 行/文件)、
两份 OOXML schema 转储、一堆 HTML 模板。**那是片 I 的形态**,不是本轮要量的形态。

所以先把桶劈成两半(cap = 2,000 行/技能目录,理由写在脚本里:
**任何单个技能目录不得超过片幅的 ~10%**,否则一个技能吃掉整片,片就不再是样本):

| 子总体 | 技能目录 | 文件 | 行 | 占全桶 | 行/文件 |
|---|---|---|---|---|---|
| 批量数据尾部(超 cap) | 35 | 518 | 198,362 | 62.8% | 383 |
| **同构短文档主体**(cap 内) | 281 | 562 | 117,525 | 37.2% | 209 |

校准片从**主体**里按行数比例跨类目分层抽样,取 **118 文件 / 17,619 行 / 81 个技能目录**。
片幅**刻意对齐片 I 的行数**(17,378,差 1.4%),因为那样两片就只差一个变量:文件数。

### 3.2 三轴逐轴对比

```verify
python3 data/r11a/probes/capacity_r11a.py | sed -n '/=== L3 内部对比/,/判读/p'
```

```text
=== L3 内部对比:片 I(少文件/多行) vs 片 C(多文件/同样行数)===
             files    lines    tokens  tok/line  tok/file  tools
         I      13    17378    204337     11.76     15718     94
         C     118    17619    257770     14.63      2184    172

  行数比   1.01x
  文件比   9.08x
  token比  1.26x
  工具比   1.83x

  判读:token 比接近 1.0 => 成本随**行**;接近文件比 => 成本随**文件**。
```

**结论:文件数翻 9 倍,token 只涨 26%,工具调用涨 83%。L3 成本主要随行走。**

三轴各自的话:
- **token(最干净的一轴)**:1.26x。远离 9.08,靠近 1.01。
- **工具调用**:1.83x。**不是 1.0**——文件多确实要多开几次文件,但增幅只有文件数增幅的 1/5。
  这是"边际成本递减"的直接读数:59 个同构文件读完前几个,后面的边际成本接近零。
- **墙钟**:**本轮不用**,且理由与 R10B 不同。R10B 说它被并发污染;本轮并发度是 **3**
  而 R10B 是 **11**,**污染程度本身就不一样**,所以两轮的墙钟连相互比较都不成立。
  记录在案但不参与任何推算。

### 3.3 这两个形态能否互相外推

**能,而且这正是本轮最有用的结论。** 判据是两者的**每行成本**:
片 I 11.76 token/行,片 C 14.63 token/行,**相差仅 1.24 倍**——
而两者的"行/文件"相差 **9 倍**(1,337 vs 149)。

一个在文件密度上差 9 倍的形态对,每行成本只差 1.24 倍,意味着
**"每行"是这两个形态共同的成本单位**,"每文件"不是。所以:
**可以用其中一个的每行成本去外推另一个,误差在 ~25% 以内;不能用每文件成本外推,那会错 9 倍。**

**但要说清边界**:这个结论覆盖的是 L3 的两种已测形态(批量数据 / 同构短文档),
**不覆盖 L3 里可能存在的第三种形态**。`round=R11` 那个 L3 桶主体是 `website/docs`,
形态上更接近片 C(短文档),但**没有实测**。这是"两个点画一条线"的固有限度。

## 4. L3 全量积压排期推算(验收项 ④)

**积压有两个读数,取决于本轮是否已落账,必须分别标注:**

| 口径 | 文件 | 行 |
|---|---|---|
| 开工时(R10B 移交项引用的那个数) | 1,878 | 584,490 |
| **收工后**(校准片 118 个已落 `R11A-aware`) | **1,760** | **566,871** |

下面的脚本读的是**当前台账**,所以打印的是收工口径:

```verify
python3 data/r11a/probes/capacity_r11a.py | sed -n '/=== 形态感知的估算/,/容量带/p'
```

```text
=== 形态感知的估算 ===
  两种形态的 token/行: 11.76(片 I,批量数据) .. 14.63(片 C,短文档) —— 相差仅 1.24x
  L3 积压 566,871 行 => 6,665,480 .. 8,293,452 token
  以 17,500 行/片 切片 => 32 片
  以 20,000 行/片 切片 => 28 片
  以 22,500 行/片 切片 => 25 片
  **约束是行不是文件**:按文件切会得出每片 3.6 万行,远超实测的 17.5k–22.5k 容量带。
```

**推算建立在几个数据点上:L3 两个(片 I、片 C),L2 十一个(R10B 十片 + 本轮片 B)。**
L2 那十一个不参与 L3 的单位成本,只用来定**容量带**(一个子代理一片能装多少行)——
那条带是 21 片实测出来的,是本推算里最扎实的一段。

**与 R10B 的对比:分歧从 4.3 倍收敛到 1.2 倍。**

| | 按行外推 | 按文件外推 | 分歧 |
|---|---|---|---|
| R10B(只有片 I) | 34 片 | 144 片 | **4.3x** |
| R11A(片 I + 片 C) | 7.72M token | 6.62M token | **1.2x** |

R10B 当时的判断是"两个都不能用,建议先跑一片校准片"——**那个判断是对的**,
而校准片跑完之后,两种方法给出的总量已经落在 20% 以内。

**排期结论**(用收工口径):L3 积压 **1,760 文件 / 566,871 行**,
**25–32 片**(按 22,500 / 17,500 行的容量带上下限),**总量 6.7M–8.3M token**。
按 R10B 十一片一轮的先例,这是 **2–3 轮**。
(用开工口径 584,490 行则是 26–33 片 / 6.9M–8.6M token;**两个口径差一个校准片,
不要混着引用**。)

**这个推算不覆盖什么(如实说)**:
1. 上面说的第三种形态风险(`website/docs` 未实测);
2. 校准片的 `status` 只走到 **L3「知悉用途」**,不是 L2;若后续决定把 `skills/` 提到 L2,
   这套单位成本**全部作废**(L2 每行 21.80 token,是 L3 的 1.5–1.9 倍);
3. 本推算用的是 **token**,不是墙钟。要排"几天做完"还需要并发度与限流信息,本轮没有。

## 5. 仓库历史统计数字的可复现性(验收项 ⑪)

R10 与 R10B 都报过"148 条 commit 带 `Claude-Session:`,160 条带任一 trailer",
并各自附了 ```` ```verify ```` 命令。命令是对的,重跑也干净。它在**完整克隆**里的答案是
**175 / 187**。

**根因:容器里的克隆是浅克隆**,一个 grafted 边界(`37e4a4d`)把从被引用 ref 可达的
历史砍掉了 40 条 commit,其中 27 条带 trailer。`git log --grep | wc -l` **分不清
"这些 commit 不匹配"和"这些 commit 不在我的克隆里"**,读者也分不清。

本轮实测两次(同一条命令、同一个 ref,只差克隆完整性):

| | `Claude-Session:` only | 任一 trailer | `rev-list --count b2d9fd5` |
|---|---|---|---|
| 浅克隆(R10/R10B 所在的容器形态) | 148 | 160 | **218** |
| 完整克隆(本轮 `git fetch --unshallow` 后) | **175** | **187** | **258** |

**多报一个 `rev-list --count` 就够了**:218 vs 258 一眼看得出克隆是短的,
而 148 vs 175 要换台机器才发现。这与 CLAUDE.md 已有的那条"负结论必须写出搜索面"同源——
**一次历史计数就是一次对 commit 的 grep,它的搜索面就是这个克隆**。

守卫脚本:`data/r11a/probes/history_stat_guard.py`(打印计数**与**分母,浅克隆时明确告警)。

**本轮所有引用仓库历史的数字一律附可达提交总数。** 本报告定稿时:`HEAD` 可达 **296** 条
(这个数会随本轮自己的 commit 增长,所以它标的是"定稿时",不是一个固定值)。
