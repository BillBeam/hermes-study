# Round 8A 报告 · 配置面

**一句话结论:配置面学透,R8 切四片,定案 71 条。**

头条发现:**同一份 `config.yaml`,Hermes 用两个装载器读,合并语义不一样。**
主装载器递归深合并,`cli.py` 那个只做一层 `dict.update`。同一个 `HERMES_HOME`、
同一份只设了两个嵌套叶子键的配置文件,跑出来 `browser.camofox` 一边 **6 个键**、
另一边 **1 个键**——用户想打开一个布尔开关,在 CLI/TUI 这一侧**顺手删掉了同级的全部默认值**。
这个例子至今没炸,是因为受害键的默认值字面量**在仓库里存在三份**,读取点自带硬编码兜底。
**但"下一个没有兜底的键"不用等——本轮实跑抓到了它。**

`agent.reasoning_effort`(思考力度开关)是**真实被支持、真实被 CLI 读取**的键
(`cli.py:8166`),它在 `cli.py` 那份默认值里、**不在 `DEFAULT_CONFIG` 里**;
而 `hermes config set` 的键名校验**只认 `DEFAULT_CONFIG`**。实跑输出原样抄录:

```
✓ Set agent.reasoning_effort = high in .../config.yaml
⚠ 'agent.reasoning_effort' is not a recognized config key — it was saved anyway, but Hermes may not read it.
  Did you mean: agent.reasoning_overrides
```

**一条完全正确的命令,得到一句假警告,外加一个会把配置弄坏的建议**——
`agent.reasoning_overrides` 的默认值是 `{}`(字典),用户照做写成字符串后
思考力度**静默失效**,而原本正确的那行已被删掉。
**头条由此从"结构性隐患"坐实为"已发生的用户可见故障"。**

**而且不是孤例。** AST 展开 `cli.py` 那份默认值得 89 键,与 `DEFAULT_CONFIG` 求差,
**28 个只存在于 CLI 一侧**(15 个是 `agent.personalities` 及其 14 个人格文本,13 个是真开关);抽 6 个实跑,
**5 个复现同样的假警告**。已确证其中 **2 个**(`agent.reasoning_effort`、
`agent.system_prompt`)既真被读、又收到假警告;其余未逐个确证,连同名单移交 R8B。

**最后一层最严重:重复的默认值会让别处正确的抽象失效。**
`tools/clarify_gateway.py` 有个解析澄清超时的函数,docstring 自称
"Single source of truth shared by every surface (messaging gateway, CLI, TUI/desktop)
so the timeout can't drift between them",解析顺序是**遗留键 `clarify.timeout` 优先、
规范键 `agent.clarify_timeout` 兜底**——设计正确,前提是没设过遗留键时它不存在。
**而 `cli.py:523` 的第二份默认值把遗留键钉死为 120。** 实测同一份只设了
`agent.clarify_timeout: 900` 的配置:**网关面 900,CLI 面 120**,三个调用点两个传 `CLI_CONFIG`。
**一个为"防止各面漂移"而写的单一真源函数,在两个面之间漂了 780 秒;
用户设的规范键在 CLI 面根本没有生效路径。** 函数本身一行没写错。
失效点距病根有三跳(第二份默认值 → 遗留键恒存在 → 优先级恒走遗留分支),
现场几乎不可能反推回去。

**对照组同样重要(否则会被误读成"这仓库到处都坏")**:同一形状在 `terminal` 上
**被正确处理了**——`cli.py:642` 明确让新键名 `backend` 压过遗留的 `env_type`,
实测有效。**差别在归一化写在哪一层**:`terminal` 那次写在 `load_cli_config` 内部
(重复默认值自己的家里),`clarify` 写在共享 helper 里,而它不知道有第二份默认值。
**教训因此比"别写两份默认值"更精确:凡依赖"这个键没被设过"的判断,
必须做在重复默认值所在的那一层。**

第二发现关乎"配置"这个词本身:**文档画的四级优先级链(CLI 参数 > `config.yaml` > `.env` >
默认值)在代码里不存在。** `config.yaml` 确实有一条统一合并链,但**环境变量根本不是其中一层**
——它只作为 `${VAR}` 的取值来源,以及被各消费点各自 `os.getenv`。而在后一种方式里,
环境变量**常常先被检查、赢过 `config.yaml`**,与文档排序正好相反。
更彻底的证据是:连读凭据的公共函数都有**两个方向相反的版本**(`get_env_value` 环境优先、
`get_env_value_prefer_dotenv` 文件优先),调用方自己挑。
R7C 移交的 QQBot 那个 bug 正长在这块无人区里——它躲开了配置系统的全部校验,
**因为它从来就不在配置系统里**。这一条本轮拿到了决定性证据:
Hermes 维护**两张** env 表(一张"运行时认识"、一张"向用户推荐"),
而这次改名在两张表里的落法**完全正确**——新名进两表并进文档,
旧名只留在"认识"表里、注释标明 `legacy aliases (pre-rename, still read for back-compat)`、
不推荐也不进文档。**整个仓库里凡走配置系统的地方都做对了,唯独 `status.py` 没跟上,
而它恰恰是直接读环境变量、绕过配置系统的那一段。**
于是这条定案从"某处笔误"升格为结构性结论:**配置系统的纪律,管不到不走配置系统的代码。**

**收尾时又推翻了自己一次,得到第三发现:两个系统之间的桥是双向的。**
`config.yaml` 里**每一个顶层标量键都会被灌进 `os.environ`**(`gateway/run.py:2058`,
仅当环境里没有同名变量)。这解释了一件否则很难理解的事——**为什么配置根层是开放世界、
不拒绝未知键**:那些键名是给技能脚本和外部程序当环境变量用的,**按定义无法穷举**。
连带更正:主线一度把 `_KNOWN_ROOT_KEYS` 当成"根键校验白名单",实际它**全仓只有一个使用点**,
且只用来给四个"看起来放错位置的 provider 字段"去重,**不拒绝任何未知根键**。
这条桥的判据是 `_key not in os.environ`,于是它是**第三处**与文档优先级相反的地方。
按此,头条那句"两个装载器"其实说少了:`config.yaml` 有**五个读取函数**
(`load_config`(含 `load_config_readonly`)/ `load_cli_config` / `read_raw_config` /
`read_user_config_raw` / 网关的 `_load_gateway_config`),**各有各的合并、缓存与优先级姿态**;
这条桥用的是 `read_user_config_raw`。
桥**必须**用原始读而不能用合并读,理由写在注释里,是一条很好的设计点:
**只有用户真正写下的键才可以被桥进环境**——若先合并默认值,
`DEFAULT_CONFIG` 的 82 个顶层键会**整体变成环境变量**。

## 3. 主要学习成果(成品章 `chapters/r8a-configuration-surface.md`)

1. **"配置"是两套几乎不相交的系统**:一份有结构、有默认值、有 schema 版本、
   有深合并的 YAML 字典;和一堆没有任何统一规则、各读各的环境变量。
   把它们当成一件事,是理解这个配置面的头号障碍。
2. **解析失败的兜底方向是"保持现状",不是"回到出厂"。** YAML 坏了不退回默认值,
   而是沿用本进程上一次成功加载的配置——因为配置里有 `approvals.deny` 这类**限制性规则**,
   退回默认值等于用户手一抖把防线拆了。
3. **读时展开密钥,写时必须还原模板。** `hermes config set` 是"读整份 → 改一个键 → 写回",
   而"读"已经把 `${VAR}` 展开成明文。若无还原机制,改一个显示选项就会把 API 密钥
   明文写进 `config.yaml`。本轮**端到端跑通验证**了两种情形都如设计所愿。
4. **缓存键必须覆盖全部输入。** 光有文件 (mtime, size) 不够,还要记下"这次展开依赖的
   环境变量当时各是什么值"——否则一次早于 `.env` 加载的 `load_config()` 会把未展开的
   字面量钉死整个进程生命周期。**"重启就好了"是缓存键不完整的典型征兆。**
5. **迁移梯:表驱动 + 支持下限 + 初始版本号不推进。** 最后一条看着别扭,
   却是从 768 行 `if` 长梯重构时**为了可证明的等价性**刻意保留的语义,并有测试断言
   新旧输出逐字相同。**重构的正确性优先于重构的美观。**
6. **一份定义,多个各自过滤的视图。** 94 条命令定义派生出四个消费面,
   每个视图的过滤规则都是隐式的;"到底有多少条命令"必须先问"对谁而言"。
7. **"粗粒度集合 + 细粒度开关"不能靠展开后判断成员。** 工具集那边踩过这个坑:
   复合工具集展开后,"从没设过"和"设了又关掉"**长得一模一样**,于是用户关掉的工具集
   重启后自己回来了。修法是换判据(显式成员优先),不是补展开逻辑。
8. **自动修正外部输入必须出声。** 凭据的 ASCII 清洗是全章最贴近用户痛点的一段:
   从 PDF/网页复制的密钥混进 Unicode 同形字,HTTP 头发不出去,供应商只回一句
   "invalid API key"。Hermes 剥掉非 ASCII **并大声警告、给出病因与处方**——
   **静默修好等于把可诊断问题变成不可诊断问题。**
9. **"配置键默认值 == 代码硬编码值"是一个可固化的陷阱判据——本轮独立出现两次。**
   `bedrock.discovery.refresh_interval: 3600` vs 常量 `3600`(键根本没接线);
   `resource_attributes["service.name"]: "hermes-gateway"` vs 被无条件覆盖成同一字面量。
   **危害在于:验证一个键最自然的做法是在默认值上跑一遍看对不对,而这时它必然假阳性。**
   两例还都伴随"同块兄弟键是好的"(bedrock 的 region/guardrail、
   `deployment.environment.name`),块级的"看起来能用"替坏键作了担保。
   **可执行的两条:审查时凡见默认值==硬编码值就专门改值验一次;
   写代码时刻意让两者不同,让"没接线"在第一次测试就暴露。**
10. **同一个语义被实现不止一次,是本簇几乎所有缺陷的共同病根——定稿时摊开数,共 17 项,
   其中 15 项已经失去同步**(完整清单见 `notes/r8a-90` §3.6;份数最多的一项是
   "某平台配好没配好",全仓 **8 份**,只有一份读运行时真值;**最基础的一项是
   "HERMES_HOME 在哪",2 份,副本漏掉了正版专门加的两道保护**)。**开轮时只数出六例:**
   两个装载器 / 三份同一默认字面量 / 两份"顶层标量→环境"的桥 / 两个方向相反的凭据读取函数 /
   一份**已经漂移**的注释模板死副本 / **两个对"cua-driver 装没装好"给出相反答案的判定**
   (后者最刺眼:规范答案已存在、docstring 还声明了自己是规范答案,安装路径就是没用它)。
   **判据不是"两份一样吗",而是"它们会不会一起改"。**
11. **跨边界对齐用了会因无关原因变化的值。** 三条缺陷同形不同装:
   遗留键名(`clarify.timeout`)、"键在哪份默认值里"(`agent.personalities`)、
   以及**拿界面文案当匹配键**(`hermes tools` 的插件注入,而稳定键 `"web"` 就在同一个 dict 里)。
   **判据:问"这个值会因为什么原因改变";只要有一条理由与对齐关系无关,它就不能当键。**
12. **分级判据必须分趟扫描。** provider 选择器把"强信号:它是激活的"与
   "弱信号:key 配齐了"写进同一趟循环,弱信号在同一次迭代里短路,
   于是**列表顺序压过信号强度**——用户回车一下就把 provider 改回了旧的。
13. **合法域含 `0` / `""` / `[]` / `False` 的配置值不能用 `or` 兜底。**
   `logging.backup_count: 0`(不留备份)静默变 3。同仓库里有写对的写法
   (判"键在不在"而非判真值)——**又一次两种写法并存**。
   `or` 链把"没设过"和"设成了假值"混为一谈,而**"显式关掉"恰恰是配置最需要能表达的意思**。
14. **接收了配置对象的函数,绝不能自己再 `load_config()`。**
   `hermes tools` 主流程持有一份 config,内层 vision 配置函数自己重载并落盘,
   回来后主流程又存了手里那份过期副本——**用户刚配好的值被清空回默认**。
   要么全程传同一份对象,要么内层把结果回传;**混用的症状是"我明明设了,一退出就没了",
   而且两个函数各自的单测都会绿。**
15. **两个各自正确的设计,合起来可以把其中一个变成空操作——而且是静默的、自报成功的。**
   本轮最锋利的一条:迁移流水线有一条写入不变式"等于默认值的一律不落盘"(理由充分,
   来自真实事故);而 v23 迁移的目的恰恰是"把 curator 那段默认值写进 `config.yaml`,
   好让用户看得见、改得动"。**两者直接互斥,不变式赢,而且赢得毫无声响。**
   主线运行时确证:屏幕打出 `✓ curator (8 default key(s))` 等 15 个键,磁盘上一个都没有。
   **三条可执行推论**:(a) "报告做了什么"必须从"实际写了什么"反算,
   而不是从"打算写什么"——本例那份成功清单是在调用写入函数**之前**填的;
   (b) 全局不变式要配一条"你的写入被我吃掉了"的回执,那个 helper 完全知道自己剥掉了什么;
   (c) 凡"为了让用户看得见而把默认值写进配置文件"的需求,先确认它与"默认值不落盘"
   是不是同一系统里的两条互斥规则——若是,正确解法是**让展示面去读默认值**,而不是写文件。
16. **共用核心 + N 个薄壳:测试覆盖的形状会与缺陷分布正交。** 配对批准两个入口
   共用同一个 `PairingStore`(核心测了 29 例),两层壳合计只有 4 例,
   而**唯一的行为分叉恰好在壳里、两边都没测**。同形但更细的一例是密钥输入:
   核心假设 `read_char()` 返回"一个逻辑按键",Windows 适配器做到了、POSIX 没有,
   于是在 Linux/macOS 上按一下 ↑ 就把 `[A` 静默写进了 API key
   (主线运行时确证:同一核心,POSIX 得 `'ab[Ac'`,Windows 得 `'abc'`)。
   **核心与壳之间的隐含契约必须写下来并被测;核心测得再密,也证明不了两个壳一致。**
17. **写"不要这样做,否则会 X"的注释时,顺手 grep 一下仓库里还有谁正在这样做。**
   本轮 `hermes_cli/gateway.py` 那段注释把"SDK 装了会盖过 token 没配、
   于是错报 ready"描述得一字不差——**而 `status.py` 今天正是这么做的**,
   隔着一个文件、同一个概念。这类注释是最好的检索线索,因为它已经把错误行为精确描述出来了。
18. **诊断工具之间自相矛盾,比单个工具不准更糟。** `hermes doctor` 催用户把
   `QQ_HOME_CHANNEL` 改成新名,而 `hermes status` 只认旧名——
   **用户是听诊断工具的话,把另一个诊断工具弄瞎的。** 用户信任诊断输出,并会照着它改配置。

## 4. 定案(`notes/r8a-90`,71 条:▲ 10 / ◇ 6 / ■ 55;另**驳回 1 条、收窄 1 条**)

### 4.1 三笔 R7C 移交项全部结案

| 移交项 | 结论 |
|---|---|
| ① `status.py` QQBot 环境变量倒置 | ✅ **成立**,并**更正来源**、**追加一条** |
| ② `commands.py` 94 条注册表定义面 | ✅ **94 确认无误**,补齐五数关系 |
| ③ `pairing.py` / `web_server.py` 批准入口 | ✅ **正面结案:不是两套判定,是一份判定 + 两层薄壳**;记三条缺陷 |

**①的更正与加强**:R7C 说"安装向导写新名"——实测新名的来源是**网关的弃用警告**
与**官方文档**(`website/docs` 中新名 3 次、旧名 0 次),不是安装向导。
**追加发现:那个兼容分支不只恒假,它的分支体还是空操作**——分支体读的是
`QQ_HOME_CHANNEL`,与三行之上主路径已经读过的是同一个变量。
**用户可复述的因果**:照官方文档配新名 → 机器人一切正常 → 但 `hermes status`
从此不再显示 home 频道。**面板惩罚了照做的人。**

**②的补齐**:94 个 `CommandDef` / 26 个别名 / 120 个可敲 token / 8 条 `gateway_only`
(带 1 别名)/ 对外扁平字典 111 条 —— 120 − 9 = 111,按类目再分加总也是 111,自洽。

**③的结论(先说好消息,这是本簇少见的"做对了")**:两把钥匙就是
`hermes_cli/pairing.py:72,74`(CLI)与 `hermes_cli/web_server.py:12337,12339`(dashboard),
全仓再无第三处批准调用点。**它们不是两套判定,而是共用同一个 `PairingStore`**——
超时、一次性、大小写、去空格、恒定时间比较(`secrets.compare_digest`)、失败计数,
**六项逐条无差异**。配对码本身也讲究:8 位、32 字符无歧义表(约 40 bit 熵)、
**明文不落盘只存加盐 SHA-256**、1 小时过期、一次性、每用户 10 分钟限流、
每平台最多 3 个待批、5 次失败锁平台 1 小时。**R7C 那句"门外那把钥匙"的答案是:
门只有一个锁芯,两把钥匙是两层薄壳。**

**三条缺陷都长在壳里**:(a) 二者**都**捅穿了 `PairingStore` 的私有成员,
为的是把"码错了"和"你被锁定了"区分开——张力是真的(对攻击者必须不可区分,
对运维者必须可区分),**方向对、实现脆**,缺的是一个明确标注"仅限已认证侧"的诊断 API(■-6);
(b) **两层壳行为不一致**:dashboard 只在"码"这条路径上报锁定(并注释了理由),
CLI 两条路径都报——运维者拿一个**已过期的 request-id** 去批准、
而平台恰好因别的原因处于锁定期时,CLI 会让他等一个与他的问题无关的计时器,
dashboard 则正确回 404(■-8);(c) **而这唯一的分叉,两条壳路都没有测**——
CLI 壳 1 例、GUI 壳 3 例,交集是 request-id 成功路;store 层测了 29 例却管不到壳(■-22)。
**这就是 (b) 能一直活着的原因:共用核心不会分叉,所以测它测不出分叉;
薄壳会分叉,而薄壳"看起来没什么逻辑,不值得测"。**

### 4.2 ▲ 组:地图与代码冲突(10 条)

- **▲-1** 代码用 `docs/design/managed-scope.md §4.1` 给最反直觉的优先级规则标出处,
  **该文件不存在**;但内容其实在 `website/docs/user-guide/managed-scope.md` 里写得很准确。
  **性质是指针失效,不是内容缺失**——不写清这一点就是夸大。
- **▲-2** 文档把 `bedrock.discovery` 的三个键讲成可调,**三个键零读取点**:
  TTL 是模块级常量,`provider_filter` 是**从没有人传的函数参数**。
  **毒性在于常量 3600 恰好等于文档里的默认值**,照文档配一遍会得出"生效了"的结论。
  同一 `bedrock:` 段下的 `region` 与 `guardrail.*` **是接了线的**,肉眼分辨不出差别。
- **▲-3** 文档的四级优先级链在代码里不存在(见头条二)。
- **▲-4** QQBot 变量名(即移交项①)。
- **▲-5** `_configure_mcp_tools_interactive` 的 docstring 说改动写成 `tools.exclude`,
  **代码写的是 `tools.include`,还主动删掉遗留的 exclude 块**。
  仓库做过一次有理由、有注释的 exclude→include 迁移(统一落盘形态),
  **唯独同函数 docstring 停在迁移之前、且停在语义正好相反的一侧**。
  危害大于一般注释腐烂:两种读法给出的"可见工具集"恰好互补。
  **这是 R7B「docstring 会说谎」、R7C「时间腐烂」之后的第三种形态:语义反转。**
- **▲-6** FAQ 两处把 DM 配对讲成"先到先得独占访问"(`faq.md:96,411`),
  **代码要求操作员批准**:入站路径只能生成一个待批的码,两个授予点都在已认证侧。
  **错的方向是让人低估暴露面**——运维者以为"我先发过消息所以别人进不来",
  于是不会去看待批队列,而那是这套机制唯一的可观测面。
  **文档写访问控制时,"谁来做那个授予动作"是不能省的主语**:
  两种模型的表面现象完全一样,所以这类错误不会被日常使用撞出来。
- **▲-7** v31 迁移的注释宣布 "The new default is OFF",**默认值至今是 `"auto"`**。
  后果是同一个版本上并存两拨行为相反的用户:升级上来的老装被一次性写成 `false`,
  全新安装拿到 `"auto"`(在 CLI/TUI/桌面上是开)。比 ▲-5 更隐蔽——
  **注释在它自己那段代码的范围内是对的,错的是它替另一个文件做的宣告。**
- **▲-8** `hermes status --all` 是**死开关**:文档写它是 "shareable redacted format",
  `--help` 写了,连测试都取名 `test_show_status_all_...` 并真的传了 `all=True`——
  而 `show_status` 全文只读 `deep`。**三条线索合起来制造了很强的"它有效"的错觉**,
  测试当然会过,因为被测代码根本不看这个参数(与 ■-20 同类)。
  顺带:那句 "redacted" 本身也不成立——脱敏只覆盖 API key(这一侧有测试守着,做得很好),
  而 home 频道(可能是手机号/邮箱/OpenID)、SSH 主机与用户名、项目绝对路径全是明文。
  **问题出在"敏感"被等同于"API key"。**
- **▲-9** 两处注释对"版本下限闸门在哪"给出相反答案(注册表说在 `run_migrations()`,
  实现说不在并解释了为什么)。以代码为准;严重度低,但**注释也有"引用失效"问题**。
- **▲-10** `atomic_config_write` 的 docstring 自称是 "The single chokepoint every
  config-update path should use",**而全仓最主要的写入者 `save_config` 绕过了它**
  (`config.py:3611` 裸调 `atomic_yaml_write`)。当前两条路等价,所以不是现在会出事的缺陷;
  **危害在时间维度上**——下一个人加固这个"唯一收口"时会合理地以为自己加固了所有写路径。
  **"唯一收口"这类制度性声明必须由一条测试或 grep 断言兑现,否则它只是一句愿望。**

### 4.5 主线驳回 1 条、收窄 1 条子代理结论(复核制度的直接产出)
