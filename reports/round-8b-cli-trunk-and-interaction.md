# Round 8B 报告 · CLI 主干与交互

**一句话结论:主干学透,两笔旧账算清,同一形状抓到九例。**

头条不是某个 bug,而是一个在本轮反复出现、且**上一轮已经撞到过一次**的形状:
**两份必须一致的东西,中间只有人。**

它有**三副**面孔,合计九例。第一副是**改了但没传到全部消费面**(3 例)。最干净的样本是一个
**从来没有显示过的启动提示**:Hermes 本该在启动时告诉你"某些工具因为缺 API key 被禁用了",
数据生产方给的字段叫 `env_vars`(`tools/registry.py:904 @ 863e313`),
而消费方用下标取的是改名前的 `missing_vars`(`cli.py:7565 @ 863e313`)。
抛出的 `KeyError` 被一个注释写着"别因为 import 出错而崩溃"、
作用域却覆盖整个函数体的 `except` 吞掉(`cli.py:7576 @ 863e313`)。
**最恶劣的一点在最后:这个异常只在"有东西要显示"时才抛**
——没有工具被禁用时列表为空、循环不进去、不抛异常。
**于是"功能坏了"和"一切正常"在屏幕上完全一样。**
而同一仓库的 `hermes doctor` **跟上了这次改名**,用的是
`item.get("missing_vars") or item.get("env_vars")`(`hermes_cli/doctor.py:2548 @ 863e313`)。
**一个消费面跟上了,另一个没有,而落后的那个是最安静的那个。**

第二副面孔是**两份必须手工对齐的名单**(5 例)。其中分歧最大的一对是两个都在枚举
"hermes 子命令名"的 frozenset:`profiles._HERMES_SUBCOMMANDS`(25 项)与
`main._BUILTIN_SUBCOMMANDS`(68 项),实跑求差**双向共 45 项不一致**
——而前者的用途正是"阻止用户把 profile 名或别名起成命令名",
于是 `dashboard`、`auth`、`backup` 等 **44 个真实命令今天都能被拿来当 profile 别名**。
另一份则已经付出用户可见的代价——"斜杠命令注册表 vs `if/elif` 分发链":
`/whoami` 在注册表里登记且不带任何 surface 限定
(`hermes_cli/commands.py:181 @ 863e313`),于是 `/help` 会列出它;
而 `cli.py` 全文**没有任何一处**提到 `whoami`——敲下去得到 "Unknown command"。
**最值得记的是仓库自己的记录**:根 `AGENTS.md:385` 声称所有消费方从注册表**自动派生**,
`AGENTS.md:402` 又要求手写一条 `elif`——**同一份文档的两句话互相矛盾,而 `/whoami` 是它的现价**。
更说明问题的是:同类问题此前已修过两次(`/indicator`、`/sessions`),
**两次都只加了针对那一条命令的回归测试,没有加"遍历注册表逐条确认分发链认识它"那条结构性断言**,
于是第三条照样漏出来。**只修实例不修判据,下一个实例一定还会来。**

**而这个形状的第三副面孔最狠:两处代码完全一致,含义却不同。**
`cli.py` 拆巨文件时把一批处理器**逐字搬进** mixin,**恰恰是"一字未改"让它坏了**——
`global _active_agent_ref` 在 `cli.py` 里绑的是 `cli` 的全局,搬进 mixin 后绑的是
**mixin 自己的**全局,于是清理逻辑读 `cli._active_agent_ref` **永远读到 `None`**,
`/exit` 时**记忆提供方的会话结束钩子从来没被触发过**(`hermes_cli/cli_agent_setup_mixin.py:520 @ 863e313`
的注释一字不差地记着这件事,并给了 issue 号 #49287)。
**教训很锋利:`global` 的含义取决于这段代码住在哪个模块,
所以它是搬家式重构里最不安全的一类语句——移动它不报错、不告警、类型检查也看不见,
只会安静地开始写另一个变量。**

**上一轮欠的两笔账(H-1 / H-2)本轮算清,而且在同一个键上合流了。**
H-2 问"浅合并的实际影响面有多大",答案比预期小得多也精确得多:
一层 `update` 只会让**三层深**的键丢兄弟,`cli.py` 的默认值里这样的子树**恰好 4 棵、共 24 个叶子**
——这是完整穷举,不是抽样。其中 **10 个被读取点的兜底救回来了**(兜底值恰好等于默认值),
**14 个没有**。没救回来的正是 `agent.personalities` 的 14 个内置人格,因为它们的兜底是 `{}`。
**实跑复现:用户在配置里加一个自己的人格,14 个内置人格全部消失**(对照组无配置时为 14)。

由此得到一条比"别写两份默认值"更可用的判据:
**浅合并的危害不取决于合并本身,取决于读取点的兜底能不能重建被删掉的东西。**
`host.docker.internal` 那种**标量**兜得回;`{}` 兜不回**十四条内容**。
**默认值装的是"内容"而不是"取值"时,浅合并一定丢内容。**

而 H-1 顺着同一个键走出了第三种后果形态。上一轮的两种是"值不同"(clarify 漂 780 秒)与"假警告";
**这一种是键的层级不同**:`agent.personalities` 只存在于 `cli.py` 那份默认值里,
主装载器的同名概念挂在**顶层**且为空(`hermes_cli/config_defaults.py:2126 @ 863e313`),
而**全部读取点读的都是 `agent.personalities`**。四个消费面实跑对照(全新安装、无 `config.yaml`):

```
1) CLI 面      cli.py:4490                  -> 14 个
2) 主装载器    load_config()                -> 0 个
3) 消息网关面  _load_gateway_config()       -> 0 个
4) TUI 网关面  server.py:5811               -> 14 个
```

**同一条 `/personality` 命令,电脑上列出 14 个内置人格,手机上通过 Slack 列出 0 个。**
连带发现顶层那个 `personalities` **没有任何读取点**(死键),
**而它的注释"add your own entries here"恰好把用户往错的层级引**,
且校验器为这个错层级专门开了绿灯(`_OPEN_DICT_TOP_LEVEL_KEYS`,`hermes_cli/config.py:4661 @ 863e313`)
——**用户写错层级不会收到任何警告**。

**把三种死法摆在一起,是本轮认为最有教学价值的一张表**,因为三者的报错信息都是"没有报错",
但排查手感完全不同:**值漂移**(读到了,值不对)、**层级错位**(某些面读不到)、
**读它的代码根本跑不到**(`display.compact` 的 `compact is not None` 恒为真,
因为形参标注是 `bool = False`——配置分支是死代码,而文档还在教用户设它)。

## 3. 主要学习成果(成品章 `chapters/r8b-cli-trunk-and-interaction.md`)

成品章按 CLAUDE.md 的六条可读性标准写成,面向"没读过本仓库、不熟 Python 异步生态"的后端工程师。
骨架:一次 `hermes -p work chat` 的走法 → 全景图 → 配置键的三种死法 →
"两份必须一致的东西"的三副面孔 → 主干上另外两个值得学的设计 → 可迁移原则 → 地图出入。

除头条外,本轮认为最值得带走的三条:

**(a) 入口顺序是一种资源,而且它会产生债务。** `-p` 决定 `HERMES_HOME`,
`HERMES_HOME` 决定读哪份配置,而很多模块在 import 那一刻就读配置
——所以 `-p` **必须在 argparse 之前**被手工扫出来(`hermes_cli/main.py:517 @ 863e313`)。
代价是一份**手抄的"带值参数"名单**(`hermes_cli/main.py:572 @ 863e313`)与真 parser 之间**没有任何自动校验**。
这笔债做得很细致(`mcp add --args` 透传区不扫描、pytest 的 `-p no:xdist` 被正则挡掉、
`sudo` 下按 `SUDO_USER` 找 profile 库),**但它仍然是本轮"手工对齐名单"四份里的第一份**。

**(b) 修复命令必须能在"被自己搞坏的环境"里跑起来。** 入口第一个 import 被 try 包着,
理由写得极具体:`hermes update` 若在 `git reset --hard` 与 `pip install -e .` 之间崩溃,
会留下"新源码 + 旧 `.pth`"的组合;**没有这个 guard,用户连修复命令都敲不进去**
(`hermes_cli/main.py:50 @ 863e313`)。同处还有一条判据很漂亮:自愈被打断的安装时
故意用**不精确**的匹配,因为"两种误判的代价不对称,选择往代价小的一侧犯错"
(`hermes_cli/main.py:11215 @ 863e313`)——**而且把这个不对称写进了注释**,
否则后人会把它"修"成精确匹配。

**(c) 当"正常完成"和"失败"用同一个异常类型表达时,必须找到区分二者的字段。**
主干为绕开旧版 Python 的子命令路由问题会**条件性地解析两次**,第一次把 stderr 换成内存缓冲吞掉。
第一版补丁让 `hermes model --help` **把帮助打了两遍**——因为 `--help` 也抛 `SystemExit`。
修法是按**退出码**区分(`hermes_cli/main.py:12507 @ 863e313`)。

### 4.2 负结论(同样是产出)

- **H-7 关闭**:没有第三个"读原始配置后落盘"的截断路径。13 行坏 YAML 实跑,
  文件 **sha1 与字节数逐位未变**。但**保护是副作用不是设计**:坏 YAML 下
  `check_config_version()` 返回 `(33, 33)`(当前==最新),迁移阶梯整个没跑。
  连带可观察后果:**配置坏掉时版本检查会报"已是最新"**。
  **公平记一条**:同一次运行 stderr 打了很明确的警告并自动存了 `.corrupt.<时间戳>.bak`,
  故只作信息记录(◇-R8B-a),不升为缺陷。
- **H-16 关闭,而且它是本仓库做对的样本**:v16 不删旧键**是有意的**,
  与 R8A ■-11 那条 780 秒漂移是**同一道题、相反结果**,差别有三处不是一处
  (旧键不进默认值 / 规范键优先 / 迁移不覆盖已有新值)。
  **由此把 R8A 的教训补全为更好用的判据:先保证"存在 == 用户设过",再让规范键赢。**
- **▲-R8B-01**:两份 TUI 判定对 `HERMES_TUI=1` 的语义分类**相反**(explicit vs ambient),
  逐个核完三个消费点后**当前无后果**——每个消费点都独立再防了一次。
  **记它的理由不是它会出事,而是它不出事的原因是纵深防御、不是优先级正确**;
  任何一处防护被当作冗余删掉,那段 docstring 里描述过的 kanban 事故就会以新形态回来。
- **◇-R8B-b**:`config.yaml` 读取函数应从 R8A 的**五个**更正为**六个**;
  第六个是 `_config_default_interface_early`(`hermes_cli/main.py:280`),
  **且它是唯一一个有正当理由的重复**——它的调用点在模块级第 371 行,
  而复用共享缓存的那个桥在第 709 行才 import 配置子系统,**371 < 709**,此时确实无缓存可用。

### 4.3 主线收窄的一条

**H-17**:锁不对称**属实**(三条改写 `_APPLIED_HOMES` 的路径只有一条持锁),
但子代理转述的"**缓存被空 dict 覆盖**"**不成立**——它是 `set`、用 `.clear()` 而非赋值,
且 CPython 下这些操作是 GIL 原子的,不会撕裂出损坏容器。
