## 2. 拆片判定:本轮吃下 **556 文件 / 191,657 行**,九片;REMAINDER 977 / 214,245 显式移交 R10B

### 2.1 判定依据

**不吃完整个 R10,是一个有依据的决定,不是没做完。**

1. **量级**:405,902 行是最大 L2 先例(R8D 83,350)的 **4.87 倍**。R9A 已判「三片不够,至少五片」。
   而"片"和"轮"是两件事:R8D 一轮跑了 4 片。要在一轮里跑完 R10 需要约 20 片,
   那不是拆分,那是把每片的深度摊薄到点名为止。
2. **主题自然断开处**:R10 里有一条清晰的接缝 —— **「内核如何被客户端接出去」**
   (协议桥 + 三种客户端的接入面)与**「桌面端的渲染层长什么样」**(816 个 React 文件)。
   前者是 harness 设计上可迁移的部分,后者是一个具体产品的界面实现。
   本轮取前者,把后者整块留给 R10B。
3. **执行验证的可得性**:`ui-tui` 与 `web` 的测试**本轮真跑通了**(165 文件 / 1,721 用例,
   见 `notes/r10-96-ts-suites.md`);`apps/desktop` 的 490 个测试文件需要 Electron 运行时,
   本容器装不动。**把能验证的部分和不能验证的部分分到两轮,比混在一轮里更诚实。**

## 3. L2「结构级理解」的交付判据(本轮定义,后续轮次与 R11 复盘照它验收)

**为什么需要它**:台账的 `layer` 列写着 L2 = 结构级理解,但"读到什么程度算读过"从来没有判据。
L1 有天然判据(逐机制、逐文件、断言带行号),L2 没有 —— 而 L2 是全仓最大的一层
(2,131 文件 / 671,639 行)。没有判据,`status` 列从 `R1-inventoried` 翻成 `R10-structure`
就只是一次改字符串。

**五条,逐条可复核:**

| # | 判据 | 怎么复核 |
|---|---|---|
| **1 点名到位** | 片内**每个文件**在底稿里至少出现一次**全路径**,并有一句话角色说明。同型薄文件可归入显式命名的组,但组内**仍逐个列出全路径** | `data/r10/probes/named_coverage.py` 逐片实测零命中数(**剔除承载清单的文件**) |
| **2 接缝穷举** | 片内每个对外接缝(JSON-RPC 方法表 / HTTP 端点表 / IPC 通道表 / 包导出表 / 事件类型表)**逐项列全、不抽样**,并给出**机械枚举命令**与条数 | 重跑它给的枚举命令,核条数。**这是最容易口头声称、最少被复核的一项** |
| **3 一条端到端链走通** | 至少一条从用户动作 → 客户端 → 协议 → Python 内核 → 回到界面的调用链,**逐跳带锚点** | 顺着锚点走一遍,看是否接得上 |
| **4 两处以上逐字取证** | 至少 2 个围栏代码块是逐字源码摘录 | `verify_citations.py` 的 BLOCK-DRIFT 全块比对 |
| **5 至少一条记号** | 至少一条 ■/▲/◇/◎ 带锚点 | 人读,抽验定性是否被证据支撑 |

**判据 2 是这套标准的重心,理由要说清**:L2 与 L1 的真实差别不是"读得浅",
而是**"读接口面而不读实现体"**。一个 14,006 行的 `tui_gateway/server.py`,
L1 的做法是逐个方法读实现,L2 的做法是**把方法表列全、把生命周期与并发模型讲清、
把实现体留给需要时再下钻**。所以 L2 可以不读实现,**但不能抽样接口** ——
接口面抽样了,"结构级理解"就退化成"看过几个文件"。

**判据 1 的一条反面教训**(H-R9D-e):点名这个动作本身会污染点名覆盖率的测量。
所以判据 1 的复核**必须**剔除承载清单的文件,`named_coverage.py` 强制要求传 `--exclude`。

## 4. 单轮容量报数(本轮为 L2/L3 建立第一个先例)

### 4.1 实测

| 口径 | 读数 |
|---|---|
| 本轮吃下(含 vendored 处置片) | **556 文件 / 191,657 行**,九片 |
| 本轮吃下(扣掉 I 片 vendored 头文件) | **554 文件 / 177,159 行**,八片精读 + 一片处置 |
| 每片平均(A–H 八片精读) | **69.3 文件 / 22,145 行** |
| 对比:唯一的 L2 先例 R8D | 4 片 / 125 文件 / 83,350 行 → 每片 **31.3 文件 / 20,838 行** |

**最稳定的那个数不是"每轮多少",是"每片多少行"**:R8D 每片 20,838 行,R10 每片 22,145 行,
两轮相差 6.3%。**而每片的文件数差了 2.2 倍**(31.3 → 69.3)——
因为界面层是大量小文件(React 组件、Ink 节点),而 R8D 读的是 `hermes_cli/` 的大文件。

**所以给后续轮的容量单位应当是「行/片」,不是「文件/片」**:约 **20,000–22,000 行一片**。
轮的容量 = 一轮跑几片 × 每片行数;R8D 跑 4 片,R10 跑 9 片。

### 4.2 推算(按本轮实测速率)

| 剩余 | 文件 | 行 | 按 ~21,500 行/片 | 按 9 片/轮 |
|---|---|---|---|---|
| **R10 REMAINDER** | 977 | 214,245 | ≈ **10 片** | **1 轮**(R10B) |
| **R11A**(运维基建,L2) | 141 | 43,365 | ≈ **2 片** | **1 轮**(远未满,可与别的欠账合并) |
| **R11B**(文档编目,L3) | 787 | 263,763 | ≈ **12 片**(**若** L3 与 L2 同速率) | **1–2 轮** |

**三条限定,必须跟着数字一起读:**

1. **R10B 那 1 轮有一个已知缺口**:`apps/desktop` 的 490 个测试文件本容器跑不动
   (需 Electron)。若 R10B 也跑不动,桌面端**整块缺执行验证**。
2. **R11A 明显偏小**(2 片 vs 本轮 9 片)。R9A 曾把"R11A 是满轮"降级为跨层外推,
   本轮实测支持那个降级:43,365 行 L2 只有本轮的 22.6%。
   **建议 R11A 与 R11B 的清账部分合并成一轮**,而不是单开。
3. **R11B 的 12 片仍是外推,不是先例。** L3 到本轮为止**仍然零先例** ——
   本轮的 13 个 L3 文件(`apps/desktop/src/i18n/*`)落在 REMAINDER 里,**本轮没碰**。
   所以「L3 单轮容量」这件事,R10 没有资格给数,**只能如实说它还是空的**。
   *(R9A 的方法学建议是"下一个做 L2 或 L3 的轮次把实际吃下多少当产出显式报数";
   本轮把 L2 那一半做了,L3 那一半仍然欠着。)*
