## 1. 第 5 项:`reading/02-principles.md` 的条目字段完整性

### 1.1 现象:59/64 有,5 条没有,而三道既有锁一条都够不到

`reading/02-principles.md` 的条目分两类:`P`(原则)64 条、`C`(跨章冲突裁定)5 条。
产物里的"字段"表现为**行首的黑体引导词**(生产者 `scripts/build_reading_layer.py:614`:`def render_entry(corpus, e, refs, conflict=False):` 就是这么排的)。逐类点数:

| 种类 | 条数 | 全类都有的字段 | 缺口 |
|---|---:|---|---|
| `P` | 64 | `源出处` 64/64 | **`陈述` 只有 59/64** —— `P60`~`P64` 一条都没有 |
| `C` | 5 | `冲突长什么样` / `裁定` / `冲突对象` / `裁定摘要` / `冲突两侧的原文` 各 5/5 | 无 |

`P60`~`P64` 是 R11F 新增的五条,它们只有 `合并` 与**机器抽取的** `源出处`。
后果不是排版难看,是**这五条把「这条原则说的是什么」整个交给了源章的原话** ——
而原则层这一层存在的全部理由,是"脱离 hermes-agent 仍然成立"。
一条没有 `陈述` 的原则,读者拿到的仍然是那一章的一段话。

**三道既有锁一条都够不到它**,这才是要记的那一点:产物由脚本生成(所以 `PRODUCT-STALE` 绿)、
源出处逐字抽取(所以锚点全对)、章节钉子全对(所以 `SECTION-DRIFT` 绿)。
「条目之间长得不一样」**不在任何一道的判据里** —— 与本轮第 4 项、与 R10B
「白名单外的锚点连分母都进不去」是同一物种:**没有判据覆盖的形状,不会让关卡变红**。

### 1.2 改法:两半互相咬住的判据

加进 `scripts/verify_reading_layer.py`(它已经是 `reading/` 的那道锁,不另起关卡):

`scripts/verify_reading_layer.py:84`

```
REQUIRED_FIELDS = {
    "P": ("陈述", "源出处"),
    "C": ("冲突长什么样", "裁定", "冲突对象", "裁定摘要", "冲突两侧的原文"),
}
```

* **`FIELD-MISSING`(阻断)**:必备字段集**显式声明**,该类每一条都必须有。
* **`FIELD-UNDECLARED`(阻断,无阈值)**:一个字段若在某类的**全部**条目里都出现,
  它就必须在声明里。

**第二条是为了堵住第一条的唯一逃生口。** 边界明令「不得以删除该字段要求的方式使关卡转绿」——
而如果只有第一条,删掉 `REQUIRED_FIELDS["P"]` 里的 `陈述` 就能转绿。加上第二条之后,
删掉它反而立刻以 `FIELD-UNDECLARED` 回来(它 64/64 全有,却不在声明里)。
负控 F2 就是**把这条路走一遍**,见 §1.4。

*为什么第二条特意做成「100% ⇒ 必须声明」而不是「≥N% ⇒ 必须声明」:
一个带阈值的判据,调阈值本身就是一条转绿的路。代价如实说 —— 它发现不了「59/64」
这种**进行中**的漂移,所以另加一行**非阻断**提示,把覆盖率 ≥50% 却未声明的字段点名
(当前唯一一条:`合并` 49/64 = 77%,它是真·可选字段,不该被逼成必备)。*

## 2. 第 6 项:`chapters/r2` 里那个以既有工程术语作外号的机制

### 2.1 是哪一个,以及它在哪里开始承担解释责任

`chapters/r2` 用了若干个借来的工程术语当外号。逐个核实"第一次承担解释责任"与"第一次被定义"
的先后(搜索面 = `chapters/r2-turn-loop-and-model-access.md` 全文,逐词 grep):

| 外号 | 首次承担解释责任 | 原先在哪定义 | 判定 |
|---|---|---|---|
| **侧车 sidecar** | **TL;DR 第 5 条结论**(全章五个最重要设计之一) | §3.8,**在它后面约 520 行** | **不合格,本轮修** |
| 游标 cursor | §3.7 | 同处即给("一个游标从头往后走") | 合格 |
| 哨兵 sentinel | §3.10 | 同处即给(`(empty)` 占位 + 不持久化标记 + 紧跟的代码块) | 合格 |
| 栅栏 fence | §4 原则 6 一句带过 | 全章无定义 | **不合格但不属本项**:它没有"在数据结构里是什么"可写,是并发原语的外号;记为观察,不在本轮改 |

**侧车是那一个。** 它在 TL;DR(`chapters/r2-turn-loop-and-model-access.md:36`)就被当成
「五个最重要设计」之一端出来,又在全景图(`:76`、`:78`)与 §3.2(`:232`)各承担一次解释,
而字面定义要到 §3.8 才出现。对那位"没读过本仓库、不熟 LLM 生态"的目标读者,
前四次出现里"侧车"只是一个听起来有道理的比喻。
*这同时违反本章自己的硬标准 1(术语锚定):TL;DR 里那段「先锚几个贯穿全章的词」
锚了 turn / tool_calls / provider / prompt cache **四个**,而"侧车"在同一段的两条之后就出现了,
没被锚。*

### 2.2 字面定义要说的三件事,逐条落在基线上

**(a) 它在数据结构里是什么** —— 一条消息上的**第二个内容字段**,名字叫 `api_content`;

### 2.3 改法

* **TL;DR 的术语锚新增一条「侧车(sidecar)」**,把 (a)(b)(c) 三件事写死,各配锚点与逐字块;
* **§3.8 那句原定义改为回指**(「它的字面定义……已在章首的术语锚里给过,这里只讲它怎么用」),
  免得同一章出现两处并列的定义,读者不知道哪个是准的;
* **§3.8 补上 (c) 的后半**(丢掉侧车为什么安全 —— 读回时那一列为空就落回 `content`),
  它原本只说"代价是一次缓存失效",没说清为什么不会发出错内容。
